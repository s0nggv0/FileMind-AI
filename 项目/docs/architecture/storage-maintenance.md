# Storage maintenance and operational diagnostics

Maintenance works only on the authenticated tenant. Its read endpoint returns bounded operation summaries, not payloads, original paths or file contents. Its check action holds the tenant storage lease, compares canonical owned originals to database references, marks missing files, and quarantines unreferenced bytes with a durable manifest. Repeated checks are idempotent. Unsafe junction ancestors are not followed.

Library and source previews receive database-derived storage health. `missing` and `not_stored` suppress original-file links and show `Original file unavailable`. Stored text, chunks and image analysis remain accessible. Future inserts with no path become `not_stored` through a trigger; read APIs also normalize old NULL paths that FORCE RLS hid during migration. Client snapshot fields do not define storage health.

The internal `removeOriginal` service validates owner, workspace, document and revision while holding the storage lease. It records removal intents before changing metadata. Clearing the active original reference, saving the workspace and committing the journal share one database transaction. Original bytes move to quarantine only after the journal proves COMMITTED. A lost response before quarantine leaves a recoverable intent. Parsed knowledge remains. No permanent-delete UI or public delete route was added.

Index UI separates the current searchable index from a building, failed or interrupted replacement. Its Retry action builds a new replacement while the current ready index stays searchable. A genuinely stale index requires rebuilding. Missing images retain saved OCR/AI analysis; rebuilding uses existing extracted content without trying to read a known missing original.

The product error boundary covers Workspace, Search, Library and Settings, with the installed Next 16.3.8 `retry` API, Back, Dashboard and Maintenance. Root-layout failures have an independent global fallback. Neither displays raw messages or stack traces.

Application logs accept a strict metadata-only schema: timestamp, level, event, request_id, workspace_id, operation_id, provider, error_code and duration. Free text, credentials, document content and vectors are rejected. Local logs rotate at 1 MiB into three backups and are excluded from builds/backups/Git. Logging is best effort; the transactional journal is the recovery authority. A logging error cannot turn a successful business transaction into a reported failure.

Planner run snapshots now retain `planner_runs`, `llm_success`, `fallback_count`, `fallback_reason`, `tool_validation_failure` and `timeout`. Reasons distinguish plan validation, plan provider failure, no selected tool, unknown tool, tool schema failure, timeout, step limit and provider failure. They contain no hidden reasoning. The Phase 7 generic fallback message cannot establish its historical root cause; new runs supply that evidence without removing the fallback.

Acceptance: 77/77 unit/integration tests passed, typecheck/lint/build passed, and 17/17 offline browser tests passed. Two isolated PostgreSQL browser cases at 1440/390 px verified missing originals, quarantine, retained lexical text/source previews and foreign-owner denial. Interrupted replacement status in that UI drill was explicitly injected; the separate real process-kill drills prove crash safety. Two bounded screenshot rounds were inspected, fixing the screenshot timing rather than altering the established design. No shipping raster was added. The existing Settings surface brief and DESIGN.md remain applicable; PRODUCT.md still describes an earlier phase and is not silently rewritten.
